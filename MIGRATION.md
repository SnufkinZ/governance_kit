# MIGRATION — installing the governance kit into a new project

The fast path is the installer:

```bash
python governance-kit/scripts/install.py <new-repo-root>          # core install
python governance-kit/scripts/install.py <new-repo-root> --with-ci # + CI workflow
```

It copies every file below to its target path, never overwrites anything that
exists, creates `tests/docs/__init__.py` and a stub `docs/SPEC.md`, and stamps
today's date into the priority board. This document is the same install
spelled out — read it to know what landed where and what you must edit.

|-- tests/

## 2. What must be edited after install (the installer reminds you)

| File | Edit |
|---|---|
| `CLAUDE.md` (root) | Replace every `<placeholder>`: project context, repo tree. The working rules and doc references are ready as shipped. |
| `docs/SPEC.md` | One paragraph: what this project is. |
| `docs/PRINCIPLES.md` | Replace §2 with your domain principle, or delete it and keep Decoupling only. |
| `scripts/check_docs_sync.py` | `CODE_SCOPES` = your code roots; `CODE_EXEMPT_PREFIXES` = generated/vendored trees *under* those roots. |
| `tests/docs/test_ownership_gate.py` | Only if you changed the constants above: mirror them in the fixtures marked `PORT`. |
| `.github/workflows/ci.yml` | Only if installed: adapt Python version / dependency install to your stack. |

Everything else is copy-as-is and domain-neutral.

## 3. The doc tests are starters, not the ceiling

The kit ships working Tier 1–2 suites (`pytest tests/docs/` is green in a
fresh install; each check starts biting when its convention is first used —
first plan doc, first versioned design doc, first draft-log batch). They cover
the invariants `design_doc_sync.md` §2–§3 names: CLAUDE.md trees, link
resolution, in_process heads + Track, board coverage, draft-log inbox, Status
vs board, snapshot freshness, Version vs changelog.

Growing beyond that is a normal Phase 0 → 1 activity: every new mechanical
invariant becomes one more test in `tests/docs/` whose failure message names
the exact file and fix (`tests_docs/README.md` has the pattern). The L2↔L3
freshness pin test is deliberately *not* shipped — build it when L3 exists
(`BOOTSTRAP.md` R0.2, `design_doc_sync.md` §3.1).

## 4. Bring-up order (matches BOOTSTRAP.md §2)

1. Run the installer; make the §2 edits; commit.
2. Sanity check (§5). All three commands should run clean.
3. Write the first design doc **before** its code, from
   `docs/skill/design_template.md`; give it a `> **Code:**` line.
4. Wire CI if you did not use `--with-ci` (gate stays `--warn-only` in Phase 0).
5. Build. `python scripts/check_bootstrap_phase.py` tells you what Phase 0
   still needs; when it passes, do the Phase 0 tightening (flip the gate to
   blocking) and edit `BOOTSTRAP.md`.

## 5. Sanity check after install

```
python scripts/check_docs_sync.py --warn-only     # gate runs; no violations in a fresh repo
python scripts/check_bootstrap_phase.py           # reports Phase 0 status (exit 1 = "not yet" — expected)
pytest tests/docs/                                # all green out of the box
```

The gate needs a git base to diff against (`origin/main`, `origin/master`,
`main`, or `master`) — commit the install first in a brand-new repo.
